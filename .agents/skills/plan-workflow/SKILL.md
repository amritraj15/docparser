# Plan Workflow: Triage + 3-Phase Plan-Then-Build

A stack-agnostic methodology for non-trivial build requests. It produces three
Markdown documents per feature, stored together in a per-feature directory:

```
<plans-root>/<feature-slug>/
├── 01-overview.md          # Phase 1
├── 02-engineering-doc.md   # Phase 2
└── 03-todo.md              # Phase 3
```

`<plans-root>` defaults to `.agents/docs/plans/` if the project has no other
convention. Pick a short kebab-case `<feature-slug>` from the request (e.g.
`user-invites`, `billing-webhooks`). Reuse the same slug across all three phases.

Templates live next to this skill; read and adapt them, do not copy blindly:
- `templates/AGENTS.md` — bootstrapped once per project in Step 0 (only if missing)
- `templates/01-overview.md`
- `templates/02-engineering-doc.md`
- `templates/03-todo.md`

A worked example lives at `examples/user-deactivation/`. Skim it the first time
you use this skill.

## Step 0 — Triage (decide whether the workflow runs at all)

Run this BEFORE Phase 1. Default: apply the workflow. Apply the **direct path**
(skip planning) only if ALL of the following are true:

- ≤ 3 files changed, and
- Touches a single architectural layer, and
- No schema/data migration, and
- No new public API endpoint or contract change, and
- No new shared interface / abstraction, and
- No change to wiring files (DI container, route/endpoint registry, app bootstrap, build config), and
- User has not asked for a design / doc / multi-step plan.

If the direct path applies: tell the user you are skipping planning and why
(one sentence), implement, and stop. Do not silently skip.

If unsure between direct and plan: default to **compressed Phase 1** (see below).

### Identify the project's conventions (bootstrap `AGENTS.md` if missing)

Before Phase 1, learn the project's shape so the rest of the workflow speaks its
language. The canonical home for this is an `AGENTS.md` at the project root.

**If `AGENTS.md` exists and is non-trivial** → read it and use it as the source
of truth for the rest of the workflow. Do not rewrite it.

**If `AGENTS.md` is missing or near-empty** → bootstrap one now using
`templates/AGENTS.md`. Discover, do not guess:

1. List the project root and any monorepo sub-packages.
2. Inspect package manifests and lockfiles to identify language(s), runtime,
   framework(s), and dependency manager.
3. Read the `README`, contributing guide, and CI workflow files (`.github/workflows/`,
   `.gitlab-ci.yml`, `Justfile`, `Makefile`, etc.) to learn how this project
   builds, tests, lints, migrates, and regenerates code.
4. Walk the source tree just enough to identify the layering convention
   (where does domain logic live? transport? persistence? generated code?).
5. Note any project-specific agent skills already present in `.agents/skills/`.
6. Note obvious gotchas (codegen markers, single-package mocks, crank-style CLI
   wrappers, etc.).

Fill the template with what you found. Mark the doc clearly as auto-generated at
the top so the user knows to verify it:

```
> Auto-generated by `plan-workflow` on <YYYY-MM-DD>. Please review and correct.
```

Then run a **lightweight review** (NOT a full Phase 1 review):

1. Show the user a short summary of what you inferred (≤ 6 bullets) and point
   them to the file.
2. Ask: "This is my read of the project. Anything wrong or missing?" Give them
   the chance to correct layer names, commands, and gotchas — these feed every
   later plan.
3. Incorporate corrections and save the file.

This is a **one-time** bootstrap. On every subsequent run, just read the
existing `AGENTS.md` and proceed.

You are not designing here — just capturing enough vocabulary to write a
grounded plan instead of a generic one.

### Slug collision & archiving

Before writing Phase 1, check whether `<plans-root>/<slug>/` already exists. If it does:

- If the existing folder is for the *same* in-flight effort → continue it.
- If it is finished (`Status: Done` in the docs) → move it to
  `<plans-root>/_archived/<slug>-<YYYY-MM-DD>/` first.
- If it is unrelated and still active → pick a new slug.

Always stamp `Status: Done` and a completion date in every doc when the feature
ships, so stale plans are greppable.

## Phase 1 — Overview Plan (product + engineering surface)

Goal: a shared, high-level understanding before any detailed design. This is
deliberately surface-level. It bridges product and engineering.

**Size signal:** the whole doc should fit on roughly one screen (~40–80 lines).
If a section exceeds ~10 bullets, push that detail into Phase 2.

Do:
1. Restate the request and the problem in your own words.
2. Capture product-level features: what users get, why it matters, user stories,
   scope, and explicit non-goals.
3. Capture the engineering overview: rough approach, affected areas of the system,
   major building blocks, dependencies, and known risks/unknowns.
4. List open questions for the user.
5. Write it to `<plans-root>/<feature-slug>/01-overview.md` using the template.

**Compressed Phase 1** — allowed when the request is clearly internal / technical
with no end-user-visible behavior (e.g. "add a relay for an existing queue"). Replace
sections 2 and 3 with a 5-line stub covering request restatement, rough approach,
affected areas, and open questions. State at the top of the doc that you are using
the compressed form.

Then run the **Review Loop** (see below). Do NOT start Phase 2 until the user
approves the overview.

---

## Phase 2 — Engineering Doc (detailed design + execution plan)

Goal: a complete implementation design an engineer (or set of agents) can execute
with no ambiguity. This is where you go deep.

**Size signal:** detailed enough that another engineer could start coding without
asking questions — but no more. A typical engineering doc is 1–3 screens; if it
crosses ~250 lines, you are likely over-designing.

Before writing, load any relevant domain skills for accurate, idiomatic design.
If the project ships language/framework-specific agent skills, consult them. List
every skill you loaded in the doc header, and what you took from it. If none are
available, say so and lean on the project's existing patterns instead.

Cover, at minimum:
1. High-level architecture: components, boundaries, data flow, sequence diagrams.
2. Low-level detail using the project's actual layout (see template for a generic
   checklist — adapt it to the project's conventions discovered in Step 0).
3. Cross-cutting concerns: validation, auth, observability, caching, transactions
   / consistency, security, performance.
4. Testing strategy: unit/integration/end-to-end, what is mocked vs. live.
5. Rollout: migrations, backward compatibility, feature flags, follow-ups.
6. **Execution strategy** — see the next section; this is the part most likely
   to go wrong, so treat it as first-class.

Write it to `<plans-root>/<feature-slug>/02-engineering-doc.md` using the template.

Then run the **Review Loop**. Do NOT start implementation or Phase 3 until the user
approves the engineering doc.

### Execution strategy & parallel-write safety

Decide and document how the build will happen:

- Whether a single agent implements it, or multiple agents work in parallel.
- If multiple: break the work into tasks with **disjoint write scopes** (no two
  agents editing the same files), and define the hand-off / order for dependent
  tasks. Specify each agent's task, inputs, expected outputs, and interfaces.
- Name the exact task list that Phase 3 will track.

**Shared choke points — never assumed disjoint.** Every project has files that
many features touch in passing and that will collide under parallel writes. The
common categories:

| Category | Examples |
|----------|----------|
| Route / endpoint / resolver registries | `routes.rb`, `urls.py`, `routes.go`, Express `app.ts`, GraphQL `resolvers.ts`, `openapi.yaml` |
| App bootstrap / DI composition root | `main.*`, `Program.cs`, `Application.java`, DI container files, kernel bootstraps |
| Shared interfaces / types / contracts | ports, domain interfaces, shared `types.ts`, proto definitions |
| Generated / mocked code | mock generators, ORM codegen, gRPC stubs, OpenAPI clients — regenerated wholesale |
| Schema / migrations | sequential migration files, schema seeds, Flyway/Liquibase/Alembic/Prisma migrate dirs |
| Package manifests & lockfiles | `package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, `requirements.txt` and their locks |
| Framework / build config | `tsconfig.json`, `vite.config.*`, `Dockerfile`, CI workflows, feature-flag configs |

In Phase 2, **list the concrete files** in this project that fall into these
categories for the current feature, and prescribe a strategy for each. Default
strategies:

| Choke-point category | Default strategy |
|----------------------|------------------|
| Registries (routes, resolvers) | Serial "wiring" phase, AFTER all parallel handlers exist |
| App bootstrap / DI root | Serial wiring phase |
| Shared interfaces / contracts | Define first, in a serial pre-phase; parallel agents consume |
| Generated / mocked code | Regenerate ONCE at the end; no agent hand-edits |
| Schema / migrations | Assign each migration a sequence number in Phase 2; never auto-number in parallel |
| Package manifests / lockfiles | Single agent runs the project's tidy/sync/install command once at the end |
| Build / framework config | Serial only |

Prescribe one of three patterns in the engineering doc:

1. **Serial** — single agent end-to-end. Default for small / highly-coupled features.
2. **Parallel-then-wire** — parallel agents build isolated slices; a final serial
   phase wires registries, bootstrap, generated code, and migrations. Most common.
3. **Interface-first** — a serial pre-phase defines shared interfaces and
   migration numbers, then parallel agents consume them, then a serial wiring
   phase closes out.

Whichever you pick, list it explicitly with the per-agent write scopes in the
template's Execution Strategy table.

**Concurrent user edits:** assume exclusive write access during execution. If the
user edits a file in your assigned scope, stop, surface the conflict, and ask
which version wins. Do not blindly overwrite.

## Phase 3 — Todo Tracker (living, used during implementation)

Goal: a single source of truth for progress during the build. It is derived
directly from the Phase 2 execution plan and is updated continuously.

Do:
1. Turn the Phase 2 task list into a checklist in
   `<plans-root>/<feature-slug>/03-todo.md` using the template.
2. For each task record: status (`todo` / `in-progress` / `done` / `blocked`),
   the owner (which agent), write scope, dependencies, and links to commits/PRs.
3. During implementation, update the todo doc as work progresses — mark items
   in-progress when started and done when finished.
4. **Parallel safety:** when multiple agents run concurrently, each agent updates
   only its own task rows/section, matching its disjoint write scope from Phase 2,
   so parallel edits do not conflict. Keep per-agent sections separated.
5. Keep it current until every task is `done`; note any newly discovered work.

**Drift recovery:** if you resume work and the todo doc looks stale (last-updated
is old, statuses don't match what you see in version control), reconstruct state
first — check recent commits, open PRs, working-tree status — then update the doc
before continuing. Never trust a stale tracker blindly.

**Scope changes during execution:** any new requirement that affects Phase 1
goals OR Phase 2 architecture mandates a return to the affected phase and
re-approval. Purely additive tasks (e.g. an extra test case, an extra field on a
new struct) go straight into the Phase 3 "Newly Discovered Work" section with a
one-line note — no re-approval needed.

Phase 3 has no formal approval gate — it is the working tracker for execution.

## Review Loop (Phases 1 and 2)

> Optional but recommended for cross-functional or high-stakes plans: load the
> `plan-review` skill before asking the user for approval. It runs a structured
> multi-persona review (CEO, CTO, CIO, CFO, Business Admin, Data Analytics,
> Data Scientist, Software Engineer, Engineering Manager) and surfaces blockers,
> risks, and clarifying questions without rewriting the plan.

1. Write/update the phase document. Also update the doc's `Status:` field:
   `Draft → In Review` when you present, `In Review → Approved` when the user approves.
2. Present a concise summary to the user — at most ~10 bullets total — and point
   them to the file path. Include the open-questions list verbatim. If revising
   after comments, show only what changed (a 2–3 line diff summary), not the
   whole doc again.
3. Explicitly ask: "Please review and approve, or request changes." Do not combine
   this with unrelated questions.
4. If the user gives comments or requests changes, incorporate them, update the doc,
   and repeat from step 2.
5. Only when the user explicitly approves, move to the next phase.

**Never assume approval.** Silence or an unrelated reply is not approval.

**Pre-approval shortcut:** if the user explicitly says "you can run Phase 1 and
Phase 2 back-to-back without checking in" (or equivalent), you may collapse the
two gates into one final approval at the end of Phase 2. Default remains
per-phase gates.

---

## When you are done

1. Stamp `Status: Done` and a completion date in all three docs.
2. Ensure every task in `03-todo.md` is `done` or explicitly marked as
   follow-up under "Newly Discovered Work".
3. Mention in your final message to the user that the plan is complete and
   point them at the engineering doc for posterity.
