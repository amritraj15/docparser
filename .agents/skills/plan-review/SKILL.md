# Plan Review: Multi-Persona Verification

A disciplined, second-set-of-eyes review for plans generated by `ai-build` /
`plan-workflow`. The goal is **not** to rewrite the plan — it is to find what is
missing, ambiguous, inconsistent, or risky before code is written.

## When to use this skill

- The user explicitly asks you to review a plan.
- A Phase 1 (`01-overview.md`) or Phase 2 (`02-engineering-doc.md`) plan has just
  been drafted and the user wants structured feedback before approval.
- A plan seems large, cross-functional, or expensive and deserves scrutiny from
  multiple stakeholders.
- You are handed a plan from another source and must validate it against the
  project's conventions.

## Trigger phrase (examples)

> "Review this plan."
> "Give me a CTO / CFO / engineering perspective on the plan."
> "What is wrong with this plan?"
> "Run a multi-persona review."
> "Challenge the assumptions in this plan."

## Core principles

1. **Question-first.** Every finding must be phrased as a question, a blocker, or
   a verifiable gap. Do not simply paraphrase the plan.
2. **Token-efficient.** Use terse bullets. One finding per line. No preamble.
3. **Non-chatty.** Do not soften, apologize, or add filler. State the issue and
   the impact.
4. **Serious.** Treat security, cost, data correctness, compliance, operational
   continuity, and team execution as first-class.
5. **Grounded in the repo.** Reference actual files, conventions from `AGENTS.md`,
   and existing patterns whenever possible.
6. **Actionable.** Each finding must have a severity and a proposed next step.

## Severity classification

| Severity | Meaning | Count |
|----------|---------|-------|
| `BLOCKER` | Would likely cause the feature to fail, ship broken, violate policy, or create legal/operational risk. Must be resolved before approval. | 0 before ship |
| `RISK` | Material chance of delay, cost overrun, security weakness, or post-launch incident. Needs a mitigation owner. | Minimize |
| `QUESTION` | Ambiguity that blocks clean implementation or makes estimation impossible. Must be answered before execution. | ≤ 10 |
| `NIT` | Suggestion for clarity, consistency, or polish. Optional. | ≤ 10 |

A plan should not be approved while any `BLOCKER` or unresolved `QUESTION` remains.

## Pre-review checklist (do this first)

Before applying personas, load and verify the artifacts:

1. **Locate the plan.** Default path: `.agents/docs/plans/<feature-slug>/`. Accept
   an explicit path if the user provides one.
2. **Read the relevant docs:**
   - `01-overview.md` for Phase 1 review.
   - `02-engineering-doc.md` for Phase 2 review.
   - `03-todo.md` if implementation has started.
3. **Read `AGENTS.md`** at the project root to ground the review in actual
   conventions.
4. **Check the `Status:` field.** If the doc is `Draft`, note that the review is
   formative. If `Approved`, the review is a pre-ship audit.
5. **Verify internal consistency.** The engineering doc must not contradict the
   overview (scope, goals, non-goals, risks).

If any of these files are missing, treat that as the first finding.

## The nine review personas

Apply each lens once, in the order below. For each persona, produce at most **6**
findings. Stop early for a persona if there is nothing material to say.

Use the persona's vocabulary. Do not invent corporate theater. Each finding must
include:

- **Lens:** persona name
- **Severity:** `BLOCKER` / `RISK` / `QUESTION` / `NIT`
- **Finding:** one sentence
- **Evidence:** cite the plan section, `AGENTS.md` clause, or repo file
- **Action:** what must happen before approval

### 1. CEO — Strategy & Value

Focus: Does this feature matter? Is the problem well-defined? Is the scope
aligned with business goals? Are we building the right thing?

Check:
- Problem statement is grounded in customer/user pain, not solution preference.
- Goals link to a measurable outcome (revenue, retention, efficiency, risk reduction).
- Non-goals explicitly prevent scope creep.
- Competitive / market context is considered.
- The plan explains why now.

Typical findings:
> "What revenue or retention metric moves if this ships?"
> "Non-goals are missing GDPR / legal deletion — confirm out of scope."

### 2. CTO — Architecture & Technical Direction

Focus: Is the architecture sound? Does it fit the platform? Does it create
unacceptable tech debt or lock-in?

Check:
- High-level design uses the project's established layers and patterns.
- New abstractions are justified; old ones are reused where possible.
- Scalability, performance, and reliability are addressed for the hot path.
- Integration points with external services are explicit.
- Innovation vs. commodity choice is defensible.

Typical findings:
> "Why introduce a new queue instead of reusing the existing event bus?"
> "No SLO / latency target stated for the new endpoint."

### 3. CIO — Operations, Security & Compliance

Focus: Can this be operated safely? Does it meet security and compliance
requirements? What is the incident response surface?

Check:
- AuthN/AuthZ model is described and consistent with existing policies.
- Data classification, retention, encryption, and access controls are covered.
- Audit logging and traceability exist.
- Dependencies on new vendors / managed services are evaluated.
- Runbooks, monitoring, and rollback are addressed.
- Compliance obligations (SOC2, GDPR, HIPAA, etc.) are noted or ruled out.

Typical findings:
> "No mention of audit logs for state-changing admin actions."
> "PII is stored in a new table; confirm encryption-at-rest and DPO sign-off."

### 4. CFO — Cost & Resource Economics

Focus: What does this cost? Is the budget justified? Are there hidden or
recurring costs?

Check:
- Infrastructure costs (compute, storage, egress, third-party API calls) are
  estimated.
- Headcount / time cost is implied or stated.
- License or vendor spend is identified.
- Cost controls (quotas, budgets, rate limits) are in place.
- ROI or break-even reasoning is present for large spends.

Typical findings:
> "No estimate of per-request LLM inference cost at projected volume."
> "New managed service has per-seat pricing; confirm budget owner."

### 5. Business Admin — Process & Adoption

Focus: Will the people and processes that use this feature actually adopt it?
Does it reduce or increase administrative burden?

Check:
- User-facing workflows are clear and match real operator behavior.
- Permissions and role assignments are realistic.
- Onboarding, documentation, and training are considered.
- Error messages and support burden are addressed.
- Edge cases in business process timing are covered.

Typical findings:
> "Who approves the new 'deactivate user' action in production?"
> "No admin UI mentioned; support team will need direct API access."

### 6. Data Analytics — Measurement & Data Quality

Focus: Can we measure success? Is the data produced clean, accessible, and
useful?

Check:
- Success metrics and instrumentation are defined.
- Event/tracking schema is stable and versioned.
- Data pipelines, warehouses, or dashboards are identified.
- Data quality checks (validation, deduplication, lineage) are described.
- Privacy / PII handling in analytics is addressed.

Typical findings:
> "No telemetry event defined for the primary user action."
> "Metric 'deactivation rate' is ambiguous — per day or cumulative?"

### 7. Data Scientist — Model & Experimentation Feasibility

Focus: If ML, AI, or statistical reasoning is involved, is it feasible? Is the
data sufficient? Are experiments designed correctly?

Check:
- Training / inference data sources, volume, and freshness are stated.
- Model selection, evaluation metric, and baseline are justified.
- Bias, fairness, and explainability are considered.
- Experiment design (control, randomization, sample size) is valid.
- Model lifecycle (retraining, monitoring, rollback) is covered.
- If no ML/AI is involved, skip this lens or mark `N/A`.

Typical findings:
> "No baseline model or offline evaluation metric specified."
> "Training data distribution likely differs from production; address drift."

### 8. Software Engineer — Implementability & Quality

Focus: Can a competent engineer implement this plan without asking 50 questions?
Is the design clean, testable, and maintainable?

Check:
- File paths, function names, and interfaces are concrete.
- Edge cases, error codes, and failure modes are enumerated.
- Tests are specified at unit, integration, and e2e levels.
- Existing code patterns are followed.
- Choke-point strategy from Phase 2 is explicit and safe.
- Dependencies and versions are pinned.

Typical findings:
> "Migration number is referenced but not reserved in a serial pre-phase."
> "Handler returns 204 on duplicate request; confirm idempotency key handling."

### 9. Engineering Manager — Execution Risk

Focus: Can the team actually deliver this on time without burnout? Are
dependencies and hand-offs clear?

Check:
- Task breakdown has disjoint write scopes.
- Parallel tasks do not collide on shared files.
- Estimates are plausible (or absent, which is a finding).
- Critical path and external dependencies are highlighted.
- Rollback and feature-flag plan exist.
- Follow-up work is tracked, not forgotten.

Typical findings:
> "Tasks 3 and 4 both modify the user repository; scopes are not disjoint."
> "No rollback plan beyond 'revert the migration'."

## Output format

Write the review to a file in the same plan directory:

```
<plans-root>/<feature-slug>/00-review-<YYYYMMDD>.md
```

Use the template in `templates/review.md`. Then present a concise summary to the
user with:

- Total counts by severity.
- The top 3 blockers or unresolved questions.
- A clear ask: approve with conditions, request changes, or answer questions.

Do not dump the entire review file into chat. Point to the file path.

## Review workflow

1. **Load artifacts** (pre-review checklist).
2. **Run the nine lenses** sequentially. Produce findings in a scratch buffer.
3. **Deduplicate.** If two personas identify the same issue, keep the stronger
   severity and merge the rationale.
4. **Sort.** Blockers first, then risks, then questions, then nits. Within each
   group, sort by architectural / implementation order.
5. **Write** the review file using the template.
6. **Summarize** to the user in ≤ 12 bullets.
7. **Ask** for the user's response: approve, revise, or answer open questions.

## Integration with plan-workflow

- This skill does **not** replace the plan-workflow review loop. It augments it.
- If a plan is currently `In Review`, append the review findings to the existing
  `Review` section or create the standalone review file and link it there.
- If the user approves after review, update the plan's `Status:` to `Approved`
  and record any conditions in the `Review` section.
- Do not begin implementation until the user explicitly resolves `BLOCKER` and
  `QUESTION` items.

## Special cases

- **Plan is missing a Phase 2 doc:** review only the overview. Flag every
  engineering detail that must be resolved in Phase 2 as a `QUESTION`.
- **Plan is already in implementation:** include `03-todo.md` in the review and
  check for drift between the engineering doc and actual tasks.
- **Plan is trivial / compressed Phase 1:** still run the lenses, but expect most
  to be `N/A` or `NIT`. Focus on whether the compressed form was justified.
- **No ML/AI component:** mark the Data Scientist lens `N/A` and do not waste
  tokens inventing ML concerns.

## Anti-patterns to avoid

- Do not write a narrative essay.
- Do not repeat the plan content back to the user.
- Do not raise hypotheticals that are irrelevant to this codebase.
- Do not treat every persona as mandatory; `N/A` is acceptable.
- Do not issue approval yourself. Only the user can approve the plan.
